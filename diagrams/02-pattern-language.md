# L2：模式语言层 — 六个可组合设计模式

> 13 个 Skill 由 6 个基础模式排列组合而成。掌握模式 = 能创造无限新 Skill。

---

## 2. 每个模式的详细定义

### P1: 姿态模式（Posture Pattern）

**解决的力冲突：** AI 有海量知识，但缺少"从什么角度看"的视角选择。

```
问题：AI 被问"审查这个计划"
  → 没有姿态：列出一堆泛泛的优缺点
  → 有姿态（CEO）：问"这值得做吗？投入产出比？"
  → 有姿态（EM）：问"能不能按时做完？技术风险？"
  → 有姿态（Designer）：问"用户体验连贯吗？信息架构？"

实现方式：
  ┌─────────────────────────────────┐
  │  <role>                         │
  │    角色名 + 核心公理 + 优化目标  │
  │  </role>                        │
  │                                 │
  │  认知模式表（可选）              │
  │    模式名 → 触发条件 → 行为     │
  └─────────────────────────────────┘
```

**使用此模式的 Skill：** plan-ceo-review(4姿态), plan-eng-review, plan-design-review, review, qa, retro

**迁移规则：** 任何需要"判断"而非"执行"的 Skill 都需要姿态模式。判断的质量取决于视角的选择。

---

### P2: 检查清单模式（Checklist Pattern）

**解决的力冲突：** AI 能检查但会"觉得差不多了"就跳过剩余项。

```
问题：AI 审查代码
  → 没有清单：查了 SQL 注入，觉得安全了，跳过了 XSS/CSRF/Race Condition
  → 有清单：逐项检查，每项标记 ✓/✗/N/A，不允许跳过

实现方式：
  ┌──────────────────────────────────────┐
  │  检查类别:                            │
  │    □ 类别 1 ──── 子项 a, b, c        │
  │    □ 类别 2 ──── 子项 d, e, f        │
  │    □ 类别 N ──── 子项 ...            │
  │                                      │
  │  规则: 必须逐项输出结果，不允许批量跳过 │
  └──────────────────────────────────────┘
```

**使用此模式的 Skill：** review(CRITICAL 10类+INFORMATIONAL 10类), design-review(80项), qa(测试层级), plan-design-review(7个Pass), ship(8阶段门控)

**迁移规则：** 任何"不遗漏"比"快速完成"更重要的 Skill 都需要检查清单。清单的价值 = 防止沉默遗漏。

---

### P3: 修复循环模式（Fix-Loop Pattern）

**解决的力冲突：** 发现问题但不修复 = 浪费上下文（AI 已理解问题，切换到人类重新理解）。

```
问题：发现了 bug
  → 没有循环：生成报告，人类自己修
  → 有循环：发现 → 定位源码 → 修复 → 验证 → 自动生成回归测试

  ┌──── 发现问题 ────┐
  │                   │
  ▼                   │
  定位源码             │
  │                   │
  ▼                   │
  修复代码             │
  │                   │
  ▼                   │
  验证修复  ── 失败 ──┘
  │
  ▼ 成功
  生成回归测试
  │
  ▼
  提交 commit
```

**使用此模式的 Skill：** qa(test→fix→retest), design-review(audit→fix→re-audit), review(Fix-First自动修复), ship(测试失败→修复→重跑)

**迁移规则：** 如果 AI 有权限修改（Edit/Write 在 allowed-tools 中），就应该用修复循环而非报告模式。唯一例外：合规场景需要审计轨迹（→ 用 qa-only）。

---

### P4: 风险门控模式（Risk-Gate Pattern）

**解决的力冲突：** 自动化高效但不可逆操作可能搞砸。

```
问题：AI 要删除一个文件/修改安全配置/推送代码
  → 没有门控：直接执行，出错不可逆
  → 有门控：计算风险值，超过阈值暂停并询问人类

  ┌──── 操作 ────┐
  │               │
  ▼               │
  风险评估         │
  │               │
  ├── 低风险 ──── 自动执行 ──→ 继续
  │
  └── 高风险 ──── AskUserQuestion
                   │
                   ├── 用户批准 → 执行
                   └── 用户拒绝 → 跳过或替代方案
```

**具体实现变体：**

| Skill | 风险度量 | 阈值 |
|---|---|---|
| qa | WTF-likelihood（%） | 累计 >50% 停止 |
| design-review | WTF-likelihood（%） | 单次 >30 或累计 >20% |
| review | Fix-First 分类 | 机械问题自动修，判断问题问人 |
| ship | 版本类型 | MINOR/MAJOR 必须问人 |
| document-release | 内容类型 | 事实性自动改，叙事性问人 |

**迁移规则：** 任何有 Write/Edit 权限且操作不可逆的 Skill 都需要风险门控。门控的关键是**定义清晰的风险度量和阈值**，而非模糊的"如果你不确定就问"。

---

### P5: 数据锚定模式（Data-Anchor Pattern）

**解决的力冲突：** AI 生成的叙事可能空洞（"做得很好"），需要锚定在具体数据上。

```
问题：AI 写回顾报告
  → 没有锚定："这周团队效率很高"
  → 有锚定："47 个 commit，+3.2k LOC，测试比例 38%，最大交付是 cookie 导入系统"

  ┌──── 收集数据 ────┐
  │  git shortlog     │
  │  git diff --stat  │
  │  文件分析          │
  │  ... (12 条命令)   │
  └────────┬──────────┘
           │
           ▼
  ┌──── 计算指标 ────┐
  │  Commits: 47      │
  │  LOC: +3.2k       │
  │  Test%: 38%       │
  │  Sessions: 8      │
  └────────┬──────────┘
           │
           ▼
  ┌──── 生成叙事 ────┐      规则：每个赞美/批评
  │  基于指标写文字    │ ◄── 必须引用具体的
  │  不允许空泛赞美    │      commit 或数据点
  └───────────────────┘
```

**使用此模式的 Skill：** retro(commit数据→叙事), review(代码证据→发现), qa(测试结果→健康报告), ship(覆盖率数据→星级评分)

**迁移规则：** 任何产出"评价"或"报告"的 Skill 都应该先收集数据再写叙事。空泛的评价不仅无用，还会降低 AI 输出的可信度。

---

### P6: 持久化模式（Persistence Pattern）

**解决的力冲突：** 单次运行有效但不累积——每次都从零开始。

```
问题：上周 retro 的数据怎么和这周比较？
  → 没有持久化：无法比较，每次独立运行
  → 有持久化：JSON 快照 → 下次加载 → 计算 delta

  运行 1                    运行 2
  ┌──────┐                 ┌──────┐
  │计算指标│                 │计算指标│
  └──┬───┘                 └──┬───┘
     │                        │
     ▼                        ▼
  ┌──────────────┐      ┌──────────────┐
  │保存 JSON 快照 │      │加载上次快照   │
  │到 .context/   │      │计算 delta    │
  └──────────────┘      │保存新快照     │
                        └──────────────┘
```

**使用此模式的 Skill：**

| Skill | 持久化内容 | 存储位置 |
|---|---|---|
| retro | 指标快照 | `.context/retros/{date}.json` |
| plan-eng-review | 测试计划 | `~/.gstack/projects/test-plan.md` |
| design-review | 设计基线 | `design-baseline.json` |
| ship | CHANGELOG/VERSION | 项目根目录 |
| qa | 健康分数 | Skill 输出（被其他 Skill 读取） |

**迁移规则：** 如果一个 Skill 会运行多次且后续运行需要参考之前的结果，就需要持久化。选择 JSON（结构化数据）或 Markdown（可读文档）取决于下游消费者是程序还是人。

## 4. 用模式积木构建新 Skill 的配方

```
场景：我要做一个「安全审计 Skill」

Step 1: 选择模式组合
  P1 姿态   → ●●● （安全审计员，OWASP Top 10 视角）
  P2 清单   → ●●● （OWASP 10 类 × 每类 5 检查项 = 50 项清单）
  P3 循环   → ●●  （发现漏洞 → 修复 → 验证修复）
  P4 门控   → ●●● （安全变更必须人工确认）
  P5 锚定   → ●●  （每个发现附代码行号和 CWE 编号）
  P6 持久   → ●   （保存审计快照供对比）

Step 2: 按骨架填充（参考 L1）
  → 元数据 + 角色定义 + 步骤序列 + 规则

Step 3: 微调约束强度（参考 L3）
  → allowed-tools: 给 Edit（能修复）但不给 Bash（防止命令注入测试变成攻击）
  → 语言约束: "永远不要在报告中包含可用的 exploit payload"
```
