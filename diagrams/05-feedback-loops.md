# L5：反馈循环层 — 三层嵌套循环系统

> Meadows 的核心洞察：gstack 不是管道，是有三层嵌套反馈循环的自学习系统。

---

## 2. 内循环详解（执行级，分钟）

```
哪些 Skill 有内循环？

/qa 的测试修复循环：
  ┌─ 运行测试 ──► 发现失败 ──► 定位源码 ──► 修复 ──► 重跑测试 ─┐
  │                                                            │
  │  ◄──────────── 如果仍然失败 ────────────────────────────────┘
  │
  └──► 如果通过 → 生成回归测试 → commit

/design-review 的视觉修复循环：
  ┌─ 截图审查 ──► 发现问题 ──► CSS 修复 ──► 重新截图 ─┐
  │                                                   │
  │  ◄──────────── 如果仍然不对 ──────────────────────┘
  │
  └──► 如果满意 → commit

/review 的 Fix-First 循环：
  ┌─ 发现问题 ──► 分类（机械/判断）──┐
  │                                  │
  │              机械问题 ──► 自动修复 → commit
  │              判断问题 ──► 报告给人类
  └──────────────────────────────────┘

停止条件（防止无限循环）：
  /qa:             WTF-likelihood > 50%  → 停止修复，报告给人类
  /design-review:  WTF-likelihood > 30   → 停止修复，报告给人类
  /qa:             修复数 > 15 → 每次额外修复 +1% WTF
  通用：           3 次重试失败 → 放弃，标记为已知问题
```

## 3. 中循环详解（决策级，小时）

```
中循环 = Skill 之间的信息反馈

路径 1: review → plan 回退
  ┌── /plan-eng-review 输出架构方案
  │
  ▼
  /review 发现架构层面的问题
    例："这个 N+1 查询不是 bug，是架构选择错误"
  │
  ▼
  用户决定：回到 /plan-eng-review 修改架构
  │
  └── 重新规划 → 重新编码 → 重新 review

路径 2: qa → review 回退
  ┌── /qa 发现测试全部通过但代码质量差
  │
  ▼
  用户决定：先跑 /review 做代码审查
  │
  └── review 修复质量问题 → 重新 qa

路径 3: ship → qa 回退
  ┌── /ship 的预飞行发现测试失败
  │
  ▼
  /ship 内部自动修复简单问题
  如果修复失败 → 用户回到 /qa
  │
  └── qa 修复 → 重新 ship

路径 4: design-review ↔ design-consultation
  ┌── /design-review 发现设计系统不一致
  │
  ▼
  用户决定：需要 /design-consultation 重新设计
  │
  └── 更新 DESIGN.md → 重新实现 → 重新 design-review

关键观察：
  中循环的"回退"决定由用户做出，不是自动的。
  → 这是故意的。跨 Skill 回退是高成本决策，不应该自动化。
  → Boyd 会说这是"Orient"步骤——人类的判断力在此处不可替代。
```

## 4. 外循环详解（学习级，周）

```
外循环 = 跨周期的知识累积

循环 1: /retro 的学习循环
  ┌── 第 1 周                    第 2 周
  │   运行 /retro               运行 /retro compare
  │   输出指标 + 叙事            │
  │   保存 JSON 快照             加载上周快照
  │        │                    计算 delta
  │        └─── .context/retros/ ─── ▶ │
  │                                    ▼
  │                              "commit 数 ↑23%，测试比例 ↓5%"
  │                              "建议：下周增加测试投入"
  │                                    │
  │                                    ▼
  │                              影响下周的 /plan 姿态选择
  │                              → 选择"scope reduction"姿态
  └────────────────────────────────────────────────────────

循环 2: /document-release 的文档循环
  ┌── 发布 v1.0                  发布 v1.1
  │   /doc-release 更新文档      /doc-release 更新文档
  │   更新 CLAUDE.md              │
  │        │                     │
  │        └─── CLAUDE.md ──── ▶ │
  │                              ▼
  │                         所有 Skill 读取更新后的
  │                         CLAUDE.md 作为上下文
  │                         → 行为微调
  └────────────────────────────────────────────────────────

循环 3: /design-review 的基线循环
  ┌── 审查 v1                   审查 v2
  │   生成 design-baseline.json  加载上次基线
  │        │                    比较当前状态
  │        └─── baseline.json ─── ▶ │
  │                                 ▼
  │                          "按钮间距从 8px 退化到 4px"
  │                          → 回归检测
  └────────────────────────────────────────────────────────
```

## 5. 杠杆点分析（Meadows 12 杠杆点框架）

```
系统中改变最小力产生最大效果的点：

┌──── 高杠杆 ────────────────────────────────────────────────┐
│                                                             │
│  杠杆点 1: 姿态选择（/plan-ceo-review Step 0）              │
│  改变姿态 = 改变系统的目标函数                                │
│  → 从"scope expansion"到"scope reduction"改变所有下游行为    │
│  → 这是系统中最高的杠杆点                                    │
│                                                             │
│  杠杆点 2: 测试计划（/plan-eng-review 输出）                 │
│  测试计划定义了"什么算通过"                                   │
│  → 改变测试计划 = 改变 /qa 的通过/失败标准                   │
│  → 间接改变 /ship 能否发布                                   │
│                                                             │
│  杠杆点 3: WTF-likelihood 阈值                               │
│  控制 AI 修复的激进程度                                       │
│  → 阈值太低 = AI 什么都不敢改                                 │
│  → 阈值太高 = AI 引入更多问题                                 │
│  → 50% 是当前的校准点                                        │
│                                                             │
│  杠杆点 4: CLAUDE.md 内容                                    │
│  被所有 Skill 读取为上下文                                    │
│  → 更新 CLAUDE.md = 隐式改变所有 Skill 的行为                │
│  → /document-release 是唯一自动更新它的 Skill                │
│                                                             │
├──── 低杠杆 ────────────────────────────────────────────────┤
│                                                             │
│  单个测试用例、单条 CSS 规则、单个 commit 消息格式            │
│  → 这些改变只影响一次运行的一个步骤                           │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

## 6. 迁移时如何复制循环结构

```
不循环的系统 = 一次性工具。循环的系统 = 持续改进的引擎。

迁移清单：

□ 内循环
  □ 你的 Skill 有"发现→修复→验证"的场景吗？
  □ 如果有 → 加入 fix-loop + 停止条件（WTF-likelihood 或重试上限）
  □ 如果没有 → 是否可以加入"检查→调整→再检查"的轻量循环？

□ 中循环
  □ 你有多个 Skill 需要协作吗？
  □ 如果有 → 定义"什么条件下回退到上一个 Skill"
  □ 关键：回退决策由人类做出，不要自动化

□ 外循环
  □ 你的 Skill 会运行多次吗？
  □ 如果会 → 加入 JSON 持久化 + delta 对比
  □ 至少保存：时间戳、关键指标、版本范围
  □ 下次运行时加载并对比
```
