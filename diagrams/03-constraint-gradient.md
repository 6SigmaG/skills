# L3：约束强度层 — 五级约束梯度

> AEE 审计中发现的盲点：所有 Skill 使用五种不同强度的约束，迁移时按强度逆序失效。

---

## 1. 五级约束光谱

```
强 ◄──────────────────────────────────────────────────────► 弱
     技术不可违反                              AI 可违反但不应该

 ┌─────────┐ ┌─────────┐ ┌─────────┐ ┌─────────┐ ┌─────────┐
 │ C1 硬约束│ │ C2 结构  │ │ C3 语言  │ │ C4 姿态  │ │ C5 文化  │
 │Tool Perm │ │  Step   │ │Linguistic│ │ Posture │ │Cultural │
 │          │ │Sequence │ │  Rules  │ │Framing  │ │  Norms  │
 └─────────┘ └─────────┘ └─────────┘ └─────────┘ └─────────┘
   工具权限      步骤顺序    自然语言     角色设定     排版语气
   不给=不能做   强制先后     "永远不要"   隐式影响    最软引导
```

## 2. 各级详解

### C1: 硬约束（Tool Permissions）— 物理屏障

```
机制：allowed-tools 白名单
违反成本：技术上不可能（工具不存在于上下文中）
失效条件：永不失效（除非修改模板）

示例：
  /qa-only:  allowed-tools = [Bash, Read, AskUserQuestion, Glob, Grep]
             ❌ 没有 Edit/Write → 物理上无法修改代码

  /browse:   allowed-tools = [Bash, Read, AskUserQuestion]
             ❌ 没有 Write → 不能创建文件

  对比:
  /qa:       allowed-tools = [Bash, Read, Write, Edit, ...]
             ✅ 有 Edit → 可以修复 bug

约束强度图：
  ██████████████████████████████████████████  100% 不可违反
```

### C2: 结构约束（Step Sequence）— 流程屏障

```
机制：模板中的 Step 1, Step 2, ... Step N 强制顺序
违反成本：跳过步骤导致下游步骤缺少输入，产出质量下降
失效条件：AI 模型"觉得"某步不需要 → 跳过或合并

示例：
  /ship Step 1（预飞行）必须在 Step 2（合并）之前
    → 因为预飞行检查"是否在 base branch"
    → 如果跳过，可能直接在 main 上操作

  /retro Step 1（数据收集）必须在 Step 9（团队分析）之前
    → 因为分析需要数据
    → 如果跳过，分析会基于 AI 的"感觉"而非数据

约束强度图：
  ████████████████████████████████░░░░░░░░░  80% — AI 可能合并步骤
```

### C3: 语言约束（Linguistic Rules）— 认知屏障

```
机制：模板中的自然语言禁令和规则
违反成本：产出质量/安全性下降，但 AI 不会报错
失效条件：上下文过长时早期规则被"遗忘"；规则与当前情境矛盾时被忽略

示例：
  /review Rule 7: "永远不要为 TODO/FIXME 创建发现"
  /retro: "赞美必须锚定在具体 commit 上，'Great week' is banned"
  /document-release: "永远不要自动更新引言、哲学或安全模型"
  /qa: "如果修复改变了测试的语义意图，重写测试而非修改断言"

约束强度图：
  ██████████████████████░░░░░░░░░░░░░░░░░░░  55% — 上下文压力下可能遗忘
```

### C4: 姿态约束（Posture Framing）— 视角屏障

```
机制：角色定义和认知模式表影响 AI 的思维方向
违反成本：输出的"角度"偏离预期，但内容可能仍然正确
失效条件：当输入强烈暗示另一种视角时，AI 可能"滑动"出角色

示例：
  /plan-ceo-review 的 CEO 姿态 → 关注投资回报、市场定位
    → 滑动风险：用户输入高度技术化时，CEO 可能退化为 EM

  /qa 的 QA 负责人姿态 → 关注测试覆盖、回归风险
    → 滑动风险：发现代码结构问题时，可能退化为 code reviewer

约束强度图：
  ██████████████░░░░░░░░░░░░░░░░░░░░░░░░░░░  35% — 输入上下文可能覆盖
```

### C5: 文化约束（Cultural Norms）— 美学屏障

```
机制：排版规则、语气定义、格式偏好
违反成本：输出"看起来不对"但功能正确
失效条件：几乎总是第一个失效的约束

示例：
  /retro: "Tweetable summary" 格式要求
  /design-consultation: "SAFE/RISK 分解"标签
  /ship: CHANGELOG 条目用"你现在可以..."开头
  /document-release: "售卖测试"语气润色

约束强度图：
  █████░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░  15% — 最先退化
```

## 3. 迁移失效顺序图

```
当你把一个 Skill 迁移到新场景时，约束按以下顺序失效：

时间 →
─────────────────────────────────────────────────────────────►

╔═══════════╗
║ C5 文化    ║  ← 第一个失效：排版格式在新场景不适用
╠═══════════╣
║ C4 姿态    ║  ← 第二个失效：角色定义在新领域需要重新校准
╠═══════════╣
║ C3 语言    ║  ← 第三个失效：规则措辞需要适配新上下文
╠═══════════╣
║ C2 结构    ║  ← 第四个失效：步骤顺序可能需要调整
╠═══════════╣
║ C1 硬约束  ║  ← 最后失效（或永不失效）：工具权限通常直接可复用
╚═══════════╝

迁移检查协议：
  1. 先确认 C1（工具权限）是否需要调整 → 通常不需要
  2. 再确认 C2（步骤顺序）是否需要增删步骤
  3. 重写 C3（语言规则）适配新领域
  4. 重新校准 C4（姿态）的角色和认知模式
  5. 最后重新定义 C5（文化）的格式和语气
```
