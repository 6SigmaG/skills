# /gstack-upgrade 深度解构

> **角色：** 自更新工具（Self-Updater）
> **定位：** 自动升级 gstack 到最新版本，支持全局和 vendored 安装
> **版本：** v1.1.0
> **allowed-tools：** Bash, Read, AskUserQuestion
> **来源：** `gstack-upgrade/SKILL.md`

---

> **结构说明：** 本文采用中等结构，因为 /gstack-upgrade 虽然是工具型 Skill，但包含了有意思的安装检测和用户交互设计。

## 一、为什么需要这个 Skill

**问题：** gstack 频繁迭代（v0.6 → v0.8 在短期内发生）。用户如果不主动更新，会错过新 Skill 和 Bug 修复。

**gstack 的方案：** 一个自包含的升级系统。不依赖 npm/brew/apt 等包管理器——gstack 自己管理自己的更新。

---

## 二、用户交互设计

### 2.1 升级确认

如果未设置自动升级，弹出选项：

| 选项 | 行为 |
|------|------|
| "Yes, upgrade now" | 立即升级 |
| "Always keep me up to date" | 开启自动升级 |
| "Not now" | 跳过，但后续会再次提醒（递增间隔） |
| "Never ask again" | 永久关闭提醒 |

**递增间隔：** "Not now" 的提醒间隔递增——第一次 1 天后，第二次 3 天后，第三次 7 天后……避免骚扰但保持存在感。

---

## 三、安装检测与升级路径

### 3.1 安装类型

```
检测安装类型
       │
       ├── Git 安装（全局或本地）
       │   → git fetch + git reset
       │
       └── Vendored 安装（复制到项目中）
           → clone 新版本 → 交换目录
```

### 3.2 双安装同步

如果同时存在全局安装和项目内的 vendored 副本：

```
升级全局安装
       │
       ▼
检测项目内有 vendored 副本？
       │
       ├── 是 → 从全局安装同步到 vendored
       └── 否 → 完成
```

这确保全局和本地版本始终一致。

---

## 四、Changelog 展示

升级完成后，读取 `CHANGELOG.md` 并提取 5-7 条面向用户的要点。不是显示完整的 Changelog——太长没人看——而是**策划过的亮点**。

---

## 五、Prompt Engineering 可迁移模式

### 模式 1：递增提醒间隔
尊重用户的"不要"，但不完全放弃——间隔递增的策略在很多产品场景中通用。

### 模式 2：自包含更新
不依赖外部包管理器——用 git 和文件系统操作实现自更新，减少对外部工具的依赖。

### 模式 3：双安装同步
当工具存在多份拷贝时，自动保持一致性——用户不需要手动同步。
