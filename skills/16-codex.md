# /codex 深度解构

> **角色：** 第二意见专家（Second Opinion）
> **定位：** 用 OpenAI Codex CLI 进行独立的跨模型代码分析
> **三种模式：** Review（评审）、Challenge（对抗）、Consult（咨询）
> **allowed-tools：** Bash, Read
> **来源：** `codex/SKILL.md`

---

## 一、为什么这个 Skill 存在

**问题：** 单一 AI 模型的盲区。Claude 写的代码由 Claude 审查，存在系统性偏见——同一个模型倾向于对自己的输出"自洽"而非"批判"。

**传统方案：** 人工 Code Review，但对独立开发者或小团队来说是瓶颈。

**gstack 的方案：** 引入竞争对手的模型（OpenAI Codex）作为独立审查者。两个不同的 AI 模型看同一段代码，盲区重叠的概率大大降低。

**核心洞察：** 这是 gstack 设计哲学中"认知多样性"的极端体现——不只是换角色，而是**换整个模型**。

---

## 二、三种运行模式

### 2.1 Review 模式

```bash
/codex review
```

- 基于 diff 的代码评审
- 输出 pass/fail 判定
- 关键问题标记为 `[P1]`——触发 gate 失败
- **与 `/review` 交叉比对：** 对比 Claude 和 OpenAI 的发现，标出只有一方发现的问题

### 2.2 Challenge 模式

```bash
/codex challenge
```

- **对抗性分析**——专门找边界条件、竞态、安全漏洞
- 使用 `xhigh` 推理等级（最大推理深度）
- 目的不是改进代码，而是**试图破坏它**

### 2.3 Consult 模式

```bash
/codex <任何 prompt>
```

- 交互式咨询，支持多轮对话
- 会话 ID 持久化在 `.context/codex-session-id`
- 自动检测 plan 文件，给出结构化反馈

## 三、技术实现

### 3.1 运行参数

| 参数 | 值 |
|------|-----|
| 推理等级 | Review/Consult: `high`，Challenge: `xhigh` |
| Web 搜索 | 启用（缓存索引，无额外费用） |
| 超时 | 5 分钟 |
| 文件修改 | **禁止**（只读模式） |

### 3.2 输出处理

```
Codex 原始输出
     │
     ├─→ 提取 [codex thinking] 推理块
     ├─→ 提取命令执行记录
     ├─→ 提取 token 使用量（from stderr）
     │
     ▼
原封不动呈现给用户（不做二次加工）
```

**为什么原封不动？** 避免 Claude "翻译" OpenAI 的输出时引入偏见。用户看到的应该是 Codex 的原始判断。

## 四、跨模型比对的价值

| 场景 | Claude 独立审查 | Claude + Codex |
|------|----------------|----------------|
| 常规 Bug | ✓ 找到大部分 | ✓ 重复确认 |
| 模型盲区 | ✗ 可能遗漏 | ✓ 另一模型补上 |
| 框架特定问题 | 取决于训练数据 | 两个模型的训练数据互补 |
| 安全漏洞 | ✓ 基础检查 | ✓ Challenge 模式深度对抗 |

---

## 五、Prompt Engineering 可迁移模式

### 模式 1：跨模型交叉验证
用不同 AI 模型审查同一段代码，减少系统性偏见。

### 模式 2：只读约束
审查工具不应修改代码——保持审查的独立性。

### 模式 3：对抗性思维等级
不同任务使用不同的推理深度——普通审查 `high`，攻击性分析 `xhigh`。

### 模式 4：原始输出透传
不翻译、不总结、不过滤——让用户看到模型的原始判断。
