# /office-hours 深度解构

> **角色：** YC 合伙人（YC Partner）
> **定位：** 用六个强迫性问题重新审视产品方向，输出设计文档而非代码
> **模式：** Startup 模式（创始人诊断）+ Builder 模式（黑客协作头脑风暴）
> **allowed-tools：** Read, Glob, Grep, AskUserQuestion
> **来源：** `office-hours/SKILL.md`

---

## 一、为什么这个 Skill 存在

**问题：** 工程师和创始人容易陷入"功能思维"——直接跳到实现，而没有先质疑"这件事该不该做"。

**传统方案：** 找 YC 合伙人或导师做 Office Hours，但频率有限、等待周期长。

**gstack 的方案：** 把 YC Office Hours 的诊断方法论编码成一个 Skill。不写代码，只输出设计文档——强制你在动手之前想清楚方向。

**核心约束：** 这是 gstack 中唯一一个**明确禁止产出代码**的 Skill，只产出设计文档。这个约束本身就是设计哲学——思考和实现要分开。

## 二、双模式架构

### 2.1 模式路由

```
用户输入 /office-hours
        │
        ▼
   收集项目上下文
  （读代码库、映射结构）
        │
        ▼
   "你的目标是什么？"
        │
        ├── 创业/产品方向 ──→ Startup 模式
        │                    （诊断六问）
        │
        └── 技术/实验/学习 ──→ Builder 模式
                              （生成式提问）
```

### 2.2 Startup 模式：六个强迫性问题

这六个问题的设计遵循了"逐层收紧"的策略——从宏观到微观，从假设到证据：

| # | 问题 | 设计意图 |
|---|------|----------|
| Q1 | **需求真实性：** 如果这个产品消失了，谁会不高兴？ | 验证是否有真实需求，而非创始人臆想 |
| Q2 | **现状替代：** 用户今天的解决方案是什么？ | 理解竞争格局和用户当前的痛点程度 |
| Q3 | **极致具体：** 说出真正需要这个产品的那个人的名字 | 逼迫从抽象"用户"到具体个体 |
| Q4 | **最窄楔子：** 这周能发布什么、让人付费的最小产品？ | 对抗"完美产品"幻想，推动极速迭代 |
| Q5 | **观察发现：** 看别人用你的产品时，什么让你吃惊？ | 揭示认知盲区——用户行为 ≠ 创始人预期 |
| Q6 | **未来适配：** 3 年后你的产品是更重要还是更不重要？ | 检验长期价值和趋势匹配度 |

**Prompt Engineering 洞察：** 这些问题不是开放式讨论——每个都有明确的"判定标准"。如果创始人答不上 Q3，说明产品定位有问题。这种"不给退路"的设计比"你觉得用户是谁？"有效 10 倍。

### 2.3 Builder 模式

面向非创业场景（学生、黑客、副项目），使用更开放的生成式提问，鼓励探索和创意而非诊断。

## 三、设计文档保存机制

### 3.1 持久化路径

```
~/.gstack/projects/{slug}/{user}-{branch}-design-{datetime}.md
```

**Lineage 追踪：** 设计文档包含 `Supersedes` 字段，引用同分支上的前一个设计文档，形成版本链。这意味着你可以看到一个功能的思考演化过程。

### 3.2 为什么不存在代码库里？

设计文档存在 `~/.gstack/` 而不是项目根目录，因为：
- 不污染 git 历史
- 多分支的设计文档不会冲突
- 保持代码库干净

---

## 四、Handoff 序列——离开时的三拍

设计文档审批通过后，有一个精心设计的"退出序列"：

1. **信号反射：** 用黄金时代级别的叙事框架总结会话洞察
2. **"One more thing" 分隔符：** 制造节奏感
3. **分层 YC 申请建议：** 根据会话中创始人展现的信号强度（top/middle/base tier），给出个性化的 YC 申请建议

**为什么有 Handoff？** 这不是走形式——它把一次对话变成了可执行的下一步。创始人带走的不只是一份文档，还有一个行动计划。

---

## 五、状态协议

| 状态 | 含义 |
|------|------|
| `DONE` | 设计文档已保存，创始人认可 |
| `DONE_WITH_CONCERNS` | 文档已保存但有未解决的问题 |
| `NEEDS_CONTEXT` | 信息不足，无法给出有价值的建议 |

## 六、Prompt Engineering 可迁移模式

### 模式 1：禁止产出约束
```
You produce design documents only — no implementation, no code scaffolding
```
**价值：** 强制 LLM 留在"思考"而非"执行"模式。可用于任何需要先规划后执行的场景。

### 模式 2：强迫性问题链
每个问题都有判定标准和追问逻辑——不是松散的讨论，而是结构化的诊断。

### 模式 3：分层退出
根据会话质量动态调整退出信息的深度和建议级别。

### 模式 4：设计文档版本链
用 `Supersedes` 字段建立决策演化历史，让思考过程可追溯。
