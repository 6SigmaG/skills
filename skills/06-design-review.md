# /design-review 深度解构

> **角色：** Designer Who Codes — 懂代码的设计师
> **定位：** Live Site 视觉审计 + 逐项修复循环
> **核心机制：** 80 项视觉审查清单、CSS-first 修复策略、原子提交、设计风险启发式、回归基线
> **来源：** `design-review/SKILL.md.tmpl`

---

## 一、为什么这个 Skill 有效

大多数 AI 代码审查工具只看逻辑正确性 — "这段代码能跑吗？" `/design-review` 问的是一个完全不同的问题：**"这个页面看起来对吗？"**

这听起来很主观，但 gstack 把它变成了一个可重复的工程流程。关键在于三个设计决策：

### 1. 80 项审查清单把"品味"变成了可检查的维度

"这个页面看起来不太对"是设计师的直觉。直觉无法教给 AI。但如果你把直觉拆成 80 个具体维度 — 间距一致性、字体层级、颜色对比度、响应式断点、hover 状态 — 每一项都变成了 AI 可以检查的二元判断。

**核心洞察：** 审美直觉不可迁移，但审美直觉的**分解清单**可以迁移。gstack 不是在教 AI 有品味，而是在给 AI 一张品味的检查清单。

### 2. CSS-first 修复策略把风险降到最低

发现视觉问题后怎么修？这是设计审查最危险的环节。改错一个组件可能导致 10 个其他页面崩溃。

gstack 的解决方案是**严格的修复优先级**：

```
CSS-only fix（改样式）     → 风险 0%
JSX structure fix（改结构）→ 风险 +5%
Component refactor（重构） → 风险 +15%
```

**原文：**
> "CSS-only changes carry zero regression risk. Prefer them overwhelmingly."

**翻译：** 纯 CSS 改动的回归风险为零。压倒性地优先选择它们。

这不是随意的偏好 — 这是工程事实。CSS 改动不会影响组件的数据流、事件处理或状态管理。一个 `margin-top: 8px` 的改动不可能让登录功能失效。

### 3. 原子提交让每个修复可独立回滚

每个视觉修复都是一个独立的 commit，格式为：

```
style(design): FINDING-NNN — 修复描述
```

这意味着如果第 47 个修复引入了新问题，你可以精确地 revert 那一个 commit，而不影响前 46 个已验证的修复。

## 二、完整结构拆解

### 2.1 审计流程：发现 → 分类 → 修复 → 验证

```
┌─────────────────────────────────────────────────────┐
│  Phase 1: 视觉审计                                    │
│  打开真实浏览器 → 逐页截图 → 80 项清单逐项检查          │
│  产出：FINDING-001 到 FINDING-NNN                      │
└──────────────────────┬──────────────────────────────┘
                       │
┌──────────────────────▼──────────────────────────────┐
│  Phase 2: 风险评估                                    │
│  每个 Finding 评估修复复杂度 + 回归风险                 │
│  分类为：CSS-only / JSX / Component / Skip             │
└──────────────────────┬──────────────────────────────┘
                       │
┌──────────────────────▼──────────────────────────────┐
│  Phase 3: 逐项修复循环                                 │
│  修复 → 截图对比（before/after）→ 提交 → 下一项         │
│  每项一个 commit: style(design): FINDING-NNN           │
└──────────────────────┬──────────────────────────────┘
                       │
┌──────────────────────▼──────────────────────────────┐
│  Phase 4: 回归基线更新                                 │
│  更新 design-baseline.json → 未来的审查可以检测退化      │
└─────────────────────────────────────────────────────┘
```

### 2.2 80 项审查清单的分类

清单不是随意罗列的 80 个点。它按照**视觉层级**从宏观到微观组织：

| 层级 | 审查维度示例 | 数量（约） |
|---|---|---|
| **布局** | 页面整体结构、网格对齐、容器宽度、响应式断点 | ~15 项 |
| **排版** | 字体层级（h1-h6）、行高、字间距、段间距 | ~12 项 |
| **颜色** | 品牌色一致性、对比度（WCAG AA）、暗模式 | ~10 项 |
| **间距** | 内边距/外边距一致性、8px 网格对齐 | ~10 项 |
| **交互状态** | hover、focus、active、disabled、loading | ~12 项 |
| **组件** | 按钮尺寸统一、表单对齐、卡片阴影 | ~10 项 |
| **动效** | 过渡时长、缓动函数、加载动画 | ~5 项 |
| **可访问性** | alt 文本、焦点可见性、屏幕阅读器标签 | ~6 项 |

**设计原理：** 这个从宏观到微观的顺序不是偶然的。先检查布局，再检查排版，再检查间距 — 因为宏观问题的修复可能影响微观，反过来则不会。如果先修间距再修布局，间距修复可能被布局改动覆盖。

### 2.3 设计修复风险启发式（Design-Fix Risk Heuristic）

这是 `/design-review` 最精妙的工程决策之一。它定义了一个**量化的风险评分体系**来决定"修还是不修"：

```
基础风险分：
  revert（回滚已有样式）   +15%
  CSS-only（纯样式改动）    0%
  JSX change（结构改动）   +5%

累积因子：
  >10 fixes in session     +1%（每多一个修复，风险递增）
  unrelated file touched   +20%（碰了不相关文件）

停止条件：
  累积风险 > 20%           → 停止修复，报告剩余问题
  硬上限 cap               → 30%（绝不超过）
```

**原文：**
> "If cumulative risk exceeds 20%, stop fixing and switch to report-only mode. Hard cap at 30% — no exceptions."

**翻译：** 如果累积风险超过 20%，停止修复并切换到纯报告模式。硬上限 30% — 没有例外。

**为什么这个启发式有效：**

1. **CSS 0% 是有根据的** — 纯样式改动不触及逻辑，回归风险接近真正的零
2. **revert +15% 看似反直觉** — 回滚一个样式应该更安全吧？不。revert 意味着你在撤销别人有意为之的设计决策，你可能不了解那个决策的上下文
3. **累积因子防止"温水煮青蛙"** — 每个修复单独看都是低风险的，但 30 个低风险修复加在一起就是高风险。+1%/fix 的递增确保了这个累积效应被量化
4. **硬上限 30% 是安全网** — 即使所有修复都是 CSS-only（每个 0%），30 个修复的累积因子也会触及停止条件

**迁移价值：** 这种"风险预算"模式可以复用到任何自动修复场景。关键是：给每种修复操作一个基础风险分，加上累积因子，设定停止条件和硬上限。

### 2.4 原子提交格式

```
style(design): FINDING-042 — Fix inconsistent button padding in header nav
style(design): FINDING-043 — Align form labels to 8px grid
style(design): FINDING-044 — Add missing hover state on secondary CTA
```

**为什么用 FINDING-NNN 编号？**

1. **可追溯** — 从 commit 可以反向追踪到审计报告中的具体发现
2. **可二分** — `git bisect` 可以精确定位哪个修复引入了新问题
3. **可选择性回滚** — `git revert <FINDING-044-commit>` 只撤销那一个修复

**原文：**
> "Every fix is one commit. Every commit is one fix. No batching. No mixing. If you need to revert, you revert exactly one visual change."

**翻译：** 每个修复一个 commit。每个 commit 一个修复。不合并。不混杂。如果需要回滚，你精确回滚一个视觉改动。

### 2.5 Before/After 截图系统

每个修复前后都会生成截图对比：

```
修复 FINDING-042 前：
  → snapshot（截图）→ 保存为 before-042.png
修复代码
修复 FINDING-042 后：
  → snapshot（截图）→ 保存为 after-042.png
  → 对比：before vs after → 确认修复有效且无副作用
```

**设计原理：** 视觉问题的验证必须是**视觉的**。你不能通过跑测试来验证"按钮间距是否对齐" — 你必须看。截图对比是视觉领域的"单元测试"。

### 2.6 design-baseline.json：设计回归基线

这是 `/design-review` 的长期记忆系统。

```json
{
  "version": "1.0.0",
  "lastAudit": "2026-03-15T10:30:00Z",
  "pages": {
    "/": {
      "findings": 3,
      "resolved": 3,
      "knownIssues": []
    },
    "/dashboard": {
      "findings": 7,
      "resolved": 5,
      "knownIssues": ["FINDING-018", "FINDING-022"]
    }
  }
}
```

**用途：**
- **下次审查时**，自动对比 baseline — 新出现的视觉问题是回归（regression），已知问题不重复报告
- **knownIssues** 记录了"知道但故意不修"的问题（比如风险太高，等下个版本）
- **趋势追踪** — findings 数量是上升还是下降？设计质量在改善还是退化？

**迁移价值：** 任何审查类 Skill 都可以用 JSON baseline 实现"记忆"。关键是：记录已知问题，避免重复报告，追踪趋势。

## 三、关键设计决策深度分析

### 为什么是"Designer Who Codes"而不是"Code Reviewer for Design"？

角色定义是 "Designer Who Codes"（懂代码的设计师），而不是"审查设计的程序员"。

这个区别决定了整个 Skill 的认知姿态：

| 姿态 | 看到问题时的反应 | 产出质量 |
|---|---|---|
| 程序员审查设计 | "这个 padding 不一致" → 报告 | 发现问题但不知道怎么修 |
| 设计师写代码 | "这个 padding 不一致" → 打开 CSS → 修成 8px 网格 | 发现问题并用设计思维修复 |

**原文：**
> "You are a designer who reads and writes CSS fluently. You see the page as a user sees it, and you fix it as an engineer fixes it."

**翻译：** 你是一个流利读写 CSS 的设计师。你以用户的视角看页面，以工程师的方式修复它。

### 为什么 CSS-first 而不是 component-first？

很多开发者的本能反应是：既然要改界面，不如顺便重构组件。gstack 明确禁止这个冲动：

**原文：**
> "Do NOT refactor components during design review. Your job is visual fidelity, not architecture. A CSS fix that ships today beats a component refactor that ships next week."

**翻译：** 设计审查时不要重构组件。你的工作是视觉保真度，不是架构。今天发布的 CSS 修复胜过下周发布的组件重构。

这背后的工程逻辑是：
1. CSS 改动的 blast radius（爆炸半径）最小
2. CSS 改动不需要改测试
3. CSS 改动不会触发其他组件的重新渲染
4. CSS 改动最容易 revert

### 停止条件的博弈论

风险启发式的停止条件（>20% 停止，cap 30%）实际上是在跟 AI 的"完美主义倾向"做博弈。

Claude 看到 80 个问题时的自然倾向是：全部修完。这在大多数场景下是好的（Boil the Lake 哲学），但在设计修复场景下是危险的 — 因为每个修复都在改变用户可见的界面，累积的视觉改动可能偏离原始设计意图。

**停止条件的本质是：** 告诉 AI "你的完美主义在这里是危险的。修到够好就停。"

## 四、如何迁移到你自己的场景

### 场景 1：自动化品牌一致性审查

从 80 项清单中提取品牌相关维度（颜色、字体、Logo 使用），创建精简版 Skill：

```markdown
# 品牌一致性审查

你是品牌守护者。打开每个页面，检查：
1. 品牌色是否使用了设计系统中的变量（不是硬编码的 hex）
2. 字体是否只使用了规定的 2-3 种字体族
3. Logo 使用是否符合品牌指南（尺寸、间距、背景）
4. 语言风格是否一致（正式/非正式、人称）

每个发现用 BRAND-NNN 编号。CSS-only 修复自动执行。
```

### 场景 2：无障碍合规审查

提取可访问性维度，加入 WCAG 标准：

```markdown
# WCAG AA 合规审查

你是无障碍专家。对每个页面：
1. 对比度：所有文本/背景组合 ≥ 4.5:1（正文）/ 3:1（大标题）
2. 焦点管理：Tab 键可以到达所有交互元素，焦点顺序合理
3. 替代文本：所有图片有描述性 alt text
4. ARIA：交互组件有正确的 role 和 label

修复风险启发式同 /design-review。CSS-only 优先。
```

### 场景 3：邮件模板视觉审查

设计审查模式可以迁移到任何视觉输出：

```markdown
# 邮件模板审查

你是邮件设计师。对每个模板：
1. 在 600px 宽度下渲染正确吗？
2. 在暗模式下图片/文字可见吗？
3. CTA 按钮在移动端可点击吗（最小 44x44px）？
4. 加载慢时（图片未加载）文字内容是否完整？
```

### 关键提取物（可复用到任何视觉审查类 Skill）

1. **量化审查清单** — 把主观审美拆成可检查的二元维度
2. **修复优先级** — 低风险操作优先（CSS > JSX > 重构）
3. **风险预算** — 基础分 + 累积因子 + 停止条件 + 硬上限
4. **原子提交** — 每修一个问题提交一次，编号可追溯
5. **Before/After 验证** — 视觉问题必须用视觉方式验证
6. **Baseline JSON** — 记录已知问题，追踪趋势，防止重复报告
