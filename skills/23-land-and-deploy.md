# /land-and-deploy 深度解构

> **角色：** 发布工程师（Release Engineer）— 后半段
> **定位：** 从"PR 已批准"到"生产环境验证通过"的完整闭环
> **allowed-tools：** Bash, Read, Write, Glob, AskUserQuestion
> **来源：** `land-and-deploy/SKILL.md`

---

## 一、为什么这个 Skill 存在

**问题：** `/ship` 创建了 PR，但"合并 PR"到"确认生产环境正常"之间还有大量手动步骤——等 CI、触发部署、检查健康状态、准备回滚。

**传统方案：** 手动在 GitHub 点 Merge → 等 CI → 检查部署平台 → 手动验证。

**gstack 的方案：** 把 /ship 的"后半段"拆成独立 Skill。/ship 负责 PR 创建，/land-and-deploy 负责从合并到生产验证。一条命令完成全链路。

---

## 二、10 步工作流

```
Step 1-3: 预飞行 + 审查检查
┌────────────────────────────────┐
│ 1. 环境检测（分支、远程）        │
│ 2. 找到关联 PR                  │
│ 3. 就绪检查（CI、审查、文档）    │
│    3.5a: PR 标题/描述准确性      │
│    3.5b: 审查仪表盘              │
│    3.5c: PR body 准确性          │
│    3.5d: document-release 检查   │
│    3.5e: 就绪报告 + 确认         │
└──────────┬─────────────────────┘
           ▼
Step 4: 合并 PR
┌────────────────────────────────┐
│ squash merge（默认）             │
│ 或 merge commit（用户选择）      │
└──────────┬─────────────────────┘
           ▼
Step 5-6: 部署策略 + 等待
┌────────────────────────────────┐
│ 5. 检测部署平台                  │
│    ├── GitHub Actions workflow  │
│    ├── Fly.io / Render / Heroku │
│    ├── Vercel / Netlify (自动)  │
│    └── Custom hooks             │
│ 6. 等待部署完成                  │
└──────────┬─────────────────────┘
           ▼
Step 7-10: 验证与报告
┌────────────────────────────────┐
│ 7. Canary 验证（条件性深度）     │
│ 8. 回滚（如果需要）             │
│ 9. 部署报告                     │
│ 10. 后续建议                    │
└────────────────────────────────┘
```

## 三、部署平台自动检测

从 CLAUDE.md 的持久化配置（由 `/setup-deploy` 写入）或项目文件自动检测：

| 检测信号 | 平台 |
|---------|------|
| `fly.toml` | Fly.io |
| `render.yaml` | Render |
| `vercel.json` / `.vercel/` | Vercel |
| `netlify.toml` | Netlify |
| `.github/workflows/*deploy*` | GitHub Actions |
| `Procfile` | Heroku |

## 四、与 /ship 的分工

| 阶段 | /ship | /land-and-deploy |
|------|-------|-----------------|
| 测试 | ✓ | ─ |
| 覆盖率审计 | ✓ | ─ |
| PR 创建 | ✓ | ─ |
| PR 合并 | ─ | ✓ |
| 部署 | ─ | ✓ |
| 生产验证 | ─ | ✓ |
| 回滚 | ─ | ✓ |

**拆分原因：** /ship 是高频操作（每个 PR），/land-and-deploy 是低频高风险操作（部署到生产）。分开后可以单独审批。

---

## 五、Prompt Engineering 可迁移模式

### 模式 1：流水线阶段拆分
把长流程拆成独立 Skill，各自有独立的权限和审批要求。

### 模式 2：平台自适应
自动检测运行环境，选择正确的部署策略——无需用户手动配置。

### 模式 3：条件性深度验证
简单部署快速检查，复杂部署深度 canary 验证——根据风险级别调整验证深度。
