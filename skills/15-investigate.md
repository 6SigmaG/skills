# /investigate 深度解构

> **角色：** 调试专家（Debugger）
> **定位：** 系统化根因调试——先调查后修复，拒绝"试试看"式的修补
> **核心原则：** "NO FIXES WITHOUT ROOT CAUSE INVESTIGATION FIRST"
> **allowed-tools：** Bash, Read, Write, Edit, Glob, Grep, AskUserQuestion
> **来源：** `investigate/SKILL.md`

---

## 一、为什么这个 Skill 存在

**问题：** AI 助手遇到 Bug 时的默认行为是"猜测原因 → 直接改代码"。这在简单问题上能奏效，但在复杂系统中会制造级联问题——修了 A 坏了 B。

**传统方案：** 高级工程师的调试方法论——假设 → 验证 → 缩小范围 → 定位根因 → 最小修复。但 AI 默认不会这么做。

**gstack 的方案：** 把"禁止在确认根因前修改任何代码"编码为硬约束。这是 gstack 中少数几个带**强制行为约束**的 Skill。

## 二、四阶段工作流

```
阶段 1：根因调查              阶段 2：模式分析
┌────────────────────┐      ┌────────────────────┐
│ 收集症状            │      │ 匹配已知 Bug 签名   │
│ 阅读相关代码        │  →   │ • 竞态条件          │
│ 检查近期变更        │      │ • Nil 传播          │
│ 确定性地复现        │      │ • 状态损坏          │
└────────────────────┘      │ • 边界错误          │
                             └────────────────────┘
                                      │
                                      ▼
阶段 4：实现修复              阶段 3：假设验证
┌────────────────────┐      ┌────────────────────┐
│ 修复根因（最小 diff）│  ←   │ 用证据验证假设      │
│ 编写回归测试        │      │ 3 次失败后升级      │
│ 全量测试验证        │      │ 记录每次验证结果     │
└────────────────────┘      └────────────────────┘
```

---

## 三、关键安全机制

### 3.1 三振出局规则

如果连续 3 个假设被证伪，**停止猜测，升级问题**——向用户请求更多上下文或建议换一个调查方向。

**为什么是 3 次？** 这是"足够尝试"和"避免在错误方向上浪费时间"之间的平衡点。大多数 Bug 在 1-2 个假设内能定位。如果 3 次都失败，说明对问题的理解有根本性偏差。

### 3.2 作用域锁

调查和修复限制在受影响的模块内。**不允许"顺手"修改不相关的代码。**

### 3.3 爆炸半径检查

如果修改涉及超过 5 个文件，触发警告。大范围修改通常意味着要么没找到根因（在到处打补丁），要么问题比想象的更系统性。

### 3.4 必须复现

修复前必须能复现 Bug，修复后必须验证 Bug 消失。不允许"改了代码但没验证"。

## 四、状态协议

| 状态 | 含义 |
|------|------|
| `DONE` | 根因已找到，修复已验证 |
| `DONE_WITH_CONCERNS` | 修复了直接问题但发现了更深层的隐患 |
| `BLOCKED` | 无法定位根因，需要更多信息或权限 |
| `NEEDS_CONTEXT` | 症状描述不足以开始调查 |

---

## 五、用户沟通协议

所有与用户的交互遵循四步结构：

1. **重新定位上下文** — 让用户知道你在调查的哪个阶段
2. **用简单语言解释** — 避免技术黑话
3. **给出建议** — 基于完备性原则的推荐
4. **提供选项** — 带有工作量估算（同时给出人类团队和 AI+gstack 的时间估算）

---

## 六、与 /review 和 /qa 的关系

| Skill | 定位 | 找到 Bug 后 |
|-------|------|-------------|
| `/review` | 预防性——在代码合并前找问题 | 标记但不修复 |
| `/qa` | 测试性——通过真实操作发现问题 | 修复并写测试 |
| `/investigate` | 诊断性——已知有 Bug，找根因 | 先调查再修复 |

三者互补：`/review` 是预防，`/qa` 是发现，`/investigate` 是深度诊断。

## 七、Prompt Engineering 可迁移模式

### 模式 1：强制调查优先
```
NO FIXES WITHOUT ROOT CAUSE INVESTIGATION FIRST
```
**价值：** 对抗 LLM 的"立即行动"偏好。可用于任何需要先分析后执行的场景。

### 模式 2：三振升级
失败次数有上限——避免在错误方向上无限尝试。

### 模式 3：爆炸半径阈值
用文件数量作为"是否偏离方向"的简单指标。

### 模式 4：双时间尺度估算
同时提供"人类团队"和"AI+工具"的时间估算，帮助用户理解 AI 辅助调试的效率差异。
