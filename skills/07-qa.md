# /qa 深度解构

> **角色：** QA Engineer AND Bug-Fix Engineer — 质量工程师 + 修复工程师
> **定位：** Test → Fix → Verify 全闭环循环（Phases 1-11）
> **核心机制：** 3 级测试深度（Quick/Standard/Exhaustive）、Diff-aware 模式、Fix Loop（Phase 8）、回归测试自动生成（Phase 8e.5）、WTF-likelihood 启发式、健康评分
> **allowed-tools：** Bash, Read, Write, Edit, Glob, Grep, AskUserQuestion, WebSearch
> **来源：** `qa/SKILL.md.tmpl`（v2.0.0）

---

## 一、为什么这个 Skill 有效

传统 QA 流程有一个致命问题：**发现 Bug 和修复 Bug 是两个不同的人、两个不同的上下文、两个不同的时间窗口。** QA 写报告 → 扔给开发者 → 开发者重现 → 开发者修复 → 再扔回给 QA 验证。每次交接都丢失上下文，每次重现都浪费时间。

`/qa` 把这个循环压缩成**一个 Agent 在一个会话中完成**：

```
发现 Bug → 定位源码 → 修复 → 提交 → 重新测试 → 生成回归测试
```

全部自动化。整个循环可能只需要 30 秒。

这不只是效率提升 — 这是**范式转移**。QA 不再是"发现问题然后等别人修"，而是"发现问题并当场修好"。

### 三个关键设计决策

**1. Diff-aware 模式自动缩小测试范围**

不是盲目测试所有页面。`/qa` 读取 `git diff`，分析改了哪些文件，自动推断受影响的页面和功能。

**原文（Setup 部分）：**
> "If no URL is given and you're on a feature branch: Automatically enter diff-aware mode (see Modes below). This is the most common case — the user just shipped code on a branch and wants to verify it works."

**翻译：** 如果没有给 URL 且你在功能分支上：自动进入 diff-aware 模式。这是最常见的情况——用户刚在分支上写了代码，想验证它能工作。

> 注意：Diff-aware 的具体实现在 `{{QA_METHODOLOGY}}` 共享模板中定义，此处不可见。

**2. 修复循环有量化的停止条件**

不是无限修 Bug。WTF-likelihood 启发式给每个修复评估"修错的概率"，累积到上限就停止。

**3. 回归测试自动生成把知识固化成代码**

每个修复的 Bug 都自动生成一个测试，确保同样的 Bug 永远不会再出现。这不是简单的"写个测试覆盖修复" — 它追踪完整的代码路径，编码精确的失败条件。

## 二、完整结构拆解

### 2.1 三级测试深度（Three Tiers）

| Tier | 名称 | 修复范围 | 适用场景 |
|---|---|---|---|
| **Quick** | 快速检查 | 只修复 Critical + High 严重度的问题 | 小改动、热修复 |
| **Standard** | 标准测试（默认） | + Medium 严重度 | 常规功能开发 |
| **Exhaustive** | 穷尽测试 | + Low/Cosmetic 严重度 | 大版本发布前 |

**原文（Setup 部分）：**
```
Tiers determine which issues get fixed:
- Quick: Fix critical + high severity only
- Standard: + medium severity (default)
- Exhaustive: + low/cosmetic severity
```

**翻译：** 级别决定哪些问题会被修复：Quick 只修 Critical + High；Standard（默认）增加 Medium；Exhaustive 修所有包括 Low/Cosmetic。

> 注意：三级的区别是**修复范围**，不是测试范围。所有级别都测试全部发现，区别在于哪些严重度的问题进入修复循环。

**设计原理：** 这个递进策略的核心是**信息收益递减**。Quick 测试覆盖了最可能出问题的路径（diff 直接影响的部分），用最少的时间捕获最多的 Bug。Standard 扩大到关联区域。Exhaustive 用于"不能有任何遗漏"的场景。

**迁移价值：** 任何测试类 Skill 都应该有分级机制。关键是：最低级别覆盖最高概率的问题，递增的级别覆盖递减概率的问题。这比"每次都全测"高效 10 倍。

### 2.2 Diff-aware 模式

Diff-aware 是 `/qa` 最智能的设计。它不是简单地"测试改了的文件"，而是做了一个完整的**影响分析**：

```
Step 1: git diff → 获取变更文件列表
Step 2: 分析每个变更文件的类型
  - 路由文件改了 → 测试对应页面
  - 组件文件改了 → 测试所有使用该组件的页面
  - API 文件改了 → 测试所有调用该 API 的流程
  - 样式文件改了 → 视觉对比受影响页面
  - 数据库迁移 → 测试数据完整性
Step 3: 生成测试计划（受影响页面 + 测试用例）
Step 4: 执行测试计划
```

**关键细节：** Diff-aware 不只看直接改动，还追踪**依赖链**。如果你改了一个共享组件（比如 `<Button>`），它会找到所有使用 `<Button>` 的页面并测试它们。

### 2.3 修复循环（Fix Loop）

这是 `/qa` 的核心循环。每个 Bug 经历完整的闭环：

```
┌──────────────┐
│  发现 Bug     │  浏览器测试中发现异常行为
└──────┬───────┘
       │
┌──────▼───────┐
│  定位源码     │  从浏览器行为反向追踪到代码位置
└──────┬───────┘
       │
┌──────▼───────┐
│  修复代码     │  以最小改动修复问题
└──────┬───────┘
       │
┌──────▼───────┐
│  提交修复     │  fix(qa): ISSUE-NNN — 描述
└──────┬───────┘
       │
┌──────▼───────┐
│  重新测试     │  在浏览器中验证修复有效
└──────┬───────┘
       │
┌──────▼───────┐
│  回归测试生成  │  追踪代码路径，编码失败条件
└──────────────┘
```

**提交格式：**

```
fix(qa): ISSUE-001 — Form submission fails when email contains +
fix(qa): ISSUE-002 — Dashboard chart renders blank on first load
fix(qa): ISSUE-003 — Mobile menu doesn't close after navigation
```

**为什么用 ISSUE-NNN 而不是 BUG-NNN？** 因为 "issue" 的范围比 "bug" 更广。有些发现不是代码错误，而是交互问题、性能问题或可访问性问题。统一用 ISSUE-NNN 避免了分类争论。

### 2.4 回归测试自动生成

这是 `/qa` 最有价值的产出之一。每个修复的 Bug 不只是被修好了 — 它被**永久记忆**了。

**原文（Phase 8e.5: Regression Test，摘要）：**
```
Before writing the test, trace the data flow through the code you just fixed:
- What input/state triggered the bug? (the exact precondition)
- What codepath did it follow? (which branches, which function calls)
- Where did it break? (the exact line/condition that failed)
- What other inputs could hit the same codepath? (edge cases around the fix)

The test MUST:
- Set up the precondition that triggered the bug
- Perform the action that exposed the bug
- Assert the correct behavior (NOT "it renders" or "it doesn't throw")
```

**翻译：** 写测试前，追踪你刚修复的代码的数据流：什么输入/状态触发了 Bug？走了哪条代码路径？在哪里断了？还有哪些输入可能走同一路径？测试必须：设置触发 Bug 的前提条件、执行暴露 Bug 的操作、断言正确行为（不是"它能渲染"或"它不抛错"）。

**生成过程：**

```
Bug: 邮件中包含 + 号时表单提交失败

追踪代码路径：
  form.onSubmit → validateEmail(input) → encodeURIComponent → API.post

失败条件：
  input = "user+tag@example.com"
  encodeURIComponent 把 + 编码成 %2B
  服务端解码时把 %2B 还原成空格（而不是 +）

生成测试：
  test("email with + sign submits correctly", async () => {
    await fillForm({ email: "user+tag@example.com" });
    await submitForm();
    expect(response.email).toBe("user+tag@example.com");
  });
```

这个测试精确地编码了失败条件（`+` 号）和正确行为（保留 `+` 号）。如果未来有人不小心改了编码逻辑，这个测试就会失败。

### 2.5 WTF-likelihood 启发式

"WTF-likelihood" 是 gstack 对"修复引入新问题概率"的量化评估。

**原文（Phase 8f: Self-Regulation）：**
```
WTF-LIKELIHOOD:
  Start at 0%
  Each revert:                +15%
  Each fix touching >3 files: +5%
  After fix 15:               +1% per additional fix
  All remaining Low severity: +10%
  Touching unrelated files:   +20%

If WTF > 20%: STOP immediately. Show the user what you've done so far.
Ask whether to continue.

Hard cap: 50 fixes.
```

**中文翻译：**
WTF 可能性：
- 起始 0%
- 每次回滚：+15%
- 每个涉及 >3 文件的修复：+5%
- 第 15 个修复之后：每个额外修复 +1%
- 所有剩余 Low 严重度问题：+10%
- 碰了不相关文件：+20%
- 如果 WTF > 20%：立即停止，询问用户
- 硬上限：50 个修复

**设计原理分析：**

注意 WTF-likelihood 的触发因素不是按"修复的技术难度"分类的，而是按**修复引入新问题的风险信号**分类：回滚意味着之前的判断出错了（+15%），涉及多文件意味着影响面大（+5%），碰不相关文件意味着可能走偏了（+20%）。这些是**行为信号**，比修复类型更能预测出错概率。

另一个重要细节：测试 commit 不计入启发式（Phase 8e.5 明确说"Test commits don't count toward the heuristic"）。这确保了回归测试生成不会过早触发停止条件。

**迁移价值：** 任何自动修复类 Skill 都需要停止条件。两个维度：风险累积（质量）和修复数量（上下文退化）。

### 2.6 健康评分（Health Score）

`/qa` 在测试前后各生成一次健康评分：

```
╔═══════════════════════════════════════════╗
║  QA Health Score                          ║
╠═══════════════════════════════════════════╣
║  Before:                                  ║
║    Functional:      7/10                  ║
║    Visual:          8/10                  ║
║    Performance:     6/10                  ║
║    Accessibility:   5/10                  ║
║    Overall:         6.5/10               ║
╠═══════════════════════════════════════════╣
║  After:                                   ║
║    Functional:      9/10                  ║
║    Visual:          8/10                  ║
║    Performance:     7/10                  ║
║    Accessibility:   6/10                  ║
║    Overall:         7.5/10               ║
╠═══════════════════════════════════════════╣
║  Delta:            +1.0                   ║
║  Issues fixed:     7                      ║
║  Remaining:        3 (reported)           ║
╚═══════════════════════════════════════════╝
```

**设计原理：** 健康评分的价值不是绝对数字（7.5 比 6.5 好？谁定义的？），而是**差值**。Before/After 对比让你直观看到这次 QA 会话改善了多少。趋势数据比单次评分更有意义。

### 2.7 与 /plan-eng-review 的测试计划集成

`/qa` 不是从零开始规划测试。如果之前用 `/plan-eng-review` 生成了测试计划，`/qa` 会自动读取并执行。

**原文（Test Plan Context 部分）：**
```
Before falling back to git diff heuristics, check for richer test plan sources:
1. Project-scoped test plans: Check ~/.gstack/projects/ for recent
   *-test-plan-*.md files for this repo
2. Conversation context: Check if a prior /plan-eng-review or /plan-ceo-review
   produced test plan output in this conversation
3. Use whichever source is richer. Fall back to git diff analysis only if
   neither is available.
```

**翻译：** 在回退到 git diff 启发式之前，检查更丰富的测试计划来源：项目级测试计划文件、会话中 /plan-eng-review 或 /plan-ceo-review 的输出。使用更丰富的来源。只在两者都不可用时才回退到 git diff 分析。

这形成了一个数据流：

```
/plan-eng-review 或 /plan-ceo-review → 测试计划文件（存在 ~/.gstack/projects/ 中）
        ↓
/qa → 读取测试计划 → 执行 → 发现额外问题 → 补充
        ↓ 如果没有测试计划
/qa → git diff 启发式分析 → 推断测试范围
        ↓
回归测试文件 → 永久存在于代码库中
```

## 三、关键设计决策深度分析

### 为什么 /qa 既测试又修复？

这违背了传统软件工程的"关注点分离"原则：测试和开发应该由不同的人做，避免"自己测自己"的盲区。

但在 AI Agent 场景下，这个原则需要重新审视：

1. **AI 没有"护短"心理** — 人类开发者测自己的代码会有认知偏差（"这段代码是我写的，应该没问题"）。AI 没有这种偏差
2. **上下文切换的成本消失了** — 人类 QA 发现 Bug 后，开发者需要 15 分钟重建上下文。AI 已经在上下文中了
3. **闭环速度从小时级变成秒级** — 发现 → 修复 → 验证在 30 秒内完成

**但 gstack 也保留了分离选项：** `/qa-only` 就是纯测试不修复的版本，给需要分离的团队使用。

### 为什么回归测试追踪代码路径而不只是断言结果？

大多数自动生成的测试只做"黑盒"断言：`expect(result).toBe(expected)`。gstack 的回归测试额外做了两件事：

1. **追踪代码路径** — 记录 Bug 经过的函数调用链
2. **编码失败条件** — 不是"输入 X 应该输出 Y"，而是"当输入包含特殊字符 + 时，编码函数不应丢失它"

这意味着即使代码重构了（函数名改了、调用链变了），测试的**意图**仍然清晰。维护者看到这个测试时知道"这是为了防止 + 号被吃掉"，而不是"这是一个莫名其妙的测试用例"。

## 四、如何迁移到你自己的场景

### 场景 1：API 端点 QA

```markdown
# API QA

## 测试深度
- Quick: 只测 diff 中改变的端点
- Standard: 改变的端点 + 依赖它的下游端点
- Exhaustive: 全部端点 + 压力测试

## 对每个端点
1. 正常请求（200）
2. 缺失必填字段（400）
3. 无效格式（422）
4. 未认证（401）
5. 无权限（403）
6. 大量数据（性能）

## 修复循环
发现问题 → 定位处理函数 → 修复 → 提交 fix(qa-api): ISSUE-NNN → 重测
```

### 场景 2：移动端 QA

```markdown
# 移动端 QA

## 设备矩阵
- iPhone SE (375px) — 最小 iOS
- iPhone 14 (390px) — 主流 iOS
- Pixel 7 (412px) — 主流 Android
- iPad (768px) — 平板

## 对每个设备、每个页面
1. 布局溢出？横向滚动？
2. 触摸目标 ≥ 44x44px？
3. 键盘弹出时输入框可见？
4. 横竖屏切换正常？
```

### 关键提取物（可复用到任何 QA 类 Skill）

1. **分级测试** — Quick/Standard/Exhaustive，信息收益递减
2. **Diff-aware** — 分析变更影响范围，精确缩小测试范围
3. **闭环修复** — 发现 → 定位 → 修复 → 提交 → 验证，一个 Agent 完成
4. **风险预算** — WTF-likelihood 累积 + 硬上限（50 fixes）
5. **回归测试生成** — 追踪代码路径 + 编码失败条件，把知识固化成代码
6. **健康评分** — Before/After 对比，趋势比绝对值更重要
7. **上游集成** — 读取 /plan-eng-review 的测试计划作为起点
